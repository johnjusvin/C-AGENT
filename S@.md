discover (the entry point)
This is not really one of the 16 stages — it's the bootstrap you run first when a brand-new CIS PDF lands in the repo. It looks at the PDF, sets up the benchmark's identity (catalog key, version), and opens a landing log where every subsequent step will be recorded. Its philosophy line says it all: the pipeline only ever records what the PDF already says, never rewrites it. You run it once per standard, then the main pipeline takes over.
1. layout
The very first stage is nothing but plumbing: it creates the folder skeleton where the benchmark will live — standards/<key>/<version>/, output/<key>/<version>/stages/, and the empty subfolders each later stage will fill. It also validates the benchmark config file (benchmark.toml) so the pipeline knows the mode, capture, and platform up front. No content is extracted yet; if this stage fails, everything after it has nowhere to write.
2. inventory
Before extracting anything, the pipeline reads the whole PDF and builds a table of contents: every section, sub-section, appendix, with its page number. This is the map that tells the later stages where in a 300+ page document the controls, DEFINE/CONFIGURE tables, and appendices live. It doesn't interpret anything — it just knows "section 1.1 starts on page 12, appendix A on page 210." Everything downstream navigates using this inventory.
3. content
With the map in hand, this stage pulls out the actual control text: every control's ID, title, requirement, security level (L1/L2), profile (Server/Workstation), and whether it's scored. It's the heaviest extraction step — the raw material of the entire benchmark comes out of the PDF here. What lands in stages/03_content/ is a faithful, structured copy of what the PDF says about each control, nothing more.
4. appendix
Benchmarks don't just list rules — they carry reference material: the DEFINE / CONFIGURE service tables, firewall port requirements, and other implementation details in the appendices. This stage extracts those. Think of it as "part 2 of extraction": content got the rules, appendix gets the supporting technical tables that explain how those rules map to actual services and ports.
5. mappings
Now the pipeline builds the translation tables: which benchmark language maps to which machine-checkable behavior (e.g. "must be configured" → a config-set check, "should be enabled" → a service check), and how sections relate to controls. These mappings are what let a later stage take fuzzy English from a PDF and turn it into a precise, executable check. Still pure extraction/structuring — no commands yet.
6. finalize
The first assembly stage. It merges everything the previous stages extracted — control text, profiles, risk metadata, mappings — into a single finalized rule object per control: clean rule text, enriched title, profile tier, benchmark identity, and the STIG flag. This is the last place the data is reshaped as a whole; after this, each control is essentially "done" as a description, ready to be cut apart.
7. refine
Not every extracted control becomes a check. This stage filters: it keeps only controls that are scored/automated and applicable to the target profile, drops duplicates and profile tags that don't apply, and normalizes IDs. What survives is the definitive list of "these are the controls we will actually build commands and validations for." It's the quality gate between "everything in the PDF" and "what we ship."
8. split
The finalized list is one big blob; this stage cuts it into one JSON file per control — 06_split/<id>.json (e.g. 1.1.1.json). Each file now holds everything one control needs: title, profiles, family, risk inputs, evidence contract hints. From here on, every stage (research, commands, probe, evidence, validation, fix) works per control, reading and writing these individual artifacts. This is where the pipeline becomes parallelizable.
9. risk
A pure-math stage: for each control it computes a risk score (IR, factor 3, etc.) from the rule's text, severity, and category using fixed keyword/pattern rules — no AI, no agents, no host. The number tells consumers how much a control matters, and it feeds later prioritization. It's fast, deterministic, and identical on every run.
10. research
Only runs for "research mode" standards (like Ubuntu 22.04); bare-mode standards (Windows) skip it. For each control it consults a memory (library/research/<sha>.json): if a record exists it's a pure lookup; if not, an offline human-run agent batch produces one (CLI + web research, fan-out, ingest with confidence gating). The record contains the recommended audit command for that control plus the exact evidence the benchmark requires, and the pipeline never fabricates it — cache miss = blocked.
11. commands
This stage records the collector command for every control into output/.../09_commands/<id>.json. It does not invent commands — it's an adapter: in research mode it takes the script from the AI research record (stage 10) and binds it to the emitter prelude; in bare mode it takes the human-authored script from library/.../bare_commands/ and pins it by digest (recording the parsed fact fields from a real capture). Either way it also derives the evidence_contract (which facts and field types the command must emit) and lints the result. Output = the artifact that stage 12 will package and stage 13 will check.
12. probe
This is where commands get ready to run on a real machine. The stage packages a self-contained handoff bundle: probe_bundle.json (every complete command, verbatim), run_probe.py (stdlib-only runner), HANDOFF.md (human instructions: snapshot first, run as root with the label flag, bring the tarball back), and manifest.json (sha256 of the others, written last so a half-copied bundle is detectable). The pipeline itself never runs a command — a human carries this bundle to the VM, runs it read-only, and comes back with real evidence.
13. evidence
Takes the VM's raw capture and, control by control, answers "does this real output conform to the declared contract?" It checks freshness (the capture ran the script this repo currently ships — digest match), completeness (no timeout/truncation, exit 0), and fact-level typing (every emitted field matches its declared type; a required fact missing with no probe_error explanation is a defect). Pass → a certified evidence unit + observability matrix; fail → blocked, never faked. This is the stage that turns "bytes from a VM" into "evidence we're willing to score."
14. validation
The scoring stage. It takes each control's certified facts (e.g. value_int: 24) and runs its rule against them, producing PASS, FAIL, ERROR, or skip/N/A. The discipline: ERROR means "couldn't look" and is never scored as FAIL; no evidence at all = blocked, not passed. Output is a validation ledger plus per-control verdict records — the actual compliance result a GRC consumer will read.
15. fix
Packaging, not execution. It reads the committed remediation scripts (library/.../fix_commands/<id>.json) and their coverage manifest, and assembles them into per-control fix units. Every unit must carry the safety contract — stop-on-error directives, a GRC_FIX_DRYRUN gate that exits before mutating, a backup of prior state, and a rollback phase — and controls marked manual/declined are honestly skipped with a reason instead of being faked as fixable. The pipeline never runs a fix; it ships one.
16. bundle
The finale. It merges the command library, validation results, fix units, policies, frontend build, and MSSQL master DB into the final deployable artifacts (e.g. fix_policy/pulse_level_1_server_fix.json). This is the single deliverable the GRC platform consumes — everything the previous 15 stages produced, normalized, indexed, and shipped as one coherent package.
